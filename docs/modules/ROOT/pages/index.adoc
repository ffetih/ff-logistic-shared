= Shared
:description: What FF Logistic writes once, whichever implementation runs.

Code written once, that does not care which implementation is active (xref:ff-logistic::decisions.adoc#d1[decision 1]).

[cols="2,4,2",options="header"]
|===
| Part | What | Since

| `identity` | The facade over Keycloak, and the only process that calls it: sign-in, service tokens, users, integration clients, and the published keys (JWKS) every application verifies tokens against | S0
| `domain` | The business areas as jars: standards, warehousing, transportation, routing (xref:ff-logistic::decisions.adoc#d2[decision 2]) | S1
| `contracts` | `ff-contracts`: one example message per Kafka topic (`contracts/<topic>.json`: fields, key, what may be null, formats) and `EventContract`, the check the modulith's and the services' tests run on what they send. The analytics loader's test reads the same examples | S6
| `analytics-loader` | Deliveries from Kafka into the analytics database, tenant-locked and rolled up per month | S6
|===

Each core is a plain library under `com.siose.ff.logistics.<area>`: its `package-info.java` names the module and what it may use, and its `<Area>Area` configuration declares the area's migrations (`db/migration/<area>`, history table `<area>_flyway_history`). An application in `com.siose.ff.logistics` picks the cores up by component scanning, whether it holds one (a service) or all (the modulith).

[cols="2,4,1",options="header"]
|===
| Core | What it holds | Since

| `ff-domain-standards` | Pure functions: GS1 check digits and SSCCs, ISO 6346 container codes, transport modes and the EN 16258 / ISO 14083 emissions calculator, great-circle distances | S3
| `ff-domain-warehousing` | Warehouses, bins, ASNs, receiving into SSCC-labelled pallets: entities, repositories, use cases, the REST API under `/api/v1/wms`, and the `wms_*` tables' migrations (S3). Its API: `InboundArrivals.open(ShipmentArrival)`, which a delivery opens at the dock (S4) | S3
| `ff-domain-transportation` | Shipments over multimodal legs, their lifecycle and CO2e footprint, the REST API under `/api/v1/tms`, the `tms_*` tables; its API: the events `ShipmentProgressed` and `ShipmentDelivered` (S4); the port `DistanceLookup`, `ShipmentDeliveries` for a completed stop, and the e-CMR links (S5) | S4
| `ff-domain-routing` | Territories and route plans with time windows, put in order by nearest neighbour or Timefold over a road matrix; stop completion and the proof-of-delivery links; the REST API under `/api/v1/geo`, the `geo_*` tables. Its API: `RoadDistances` (also `GET /api/v1/geo/distance`) and the event `RouteStopCompleted` | S5
|===

A core with business rules tests them itself, once: a small Spring Boot application in its `src/test` (the same chassis as the real ones, an in-memory database migrated by the area's own scripts) runs the area's API tests. The modulith and the services only check that they serve the area.

[source,bash]
----
./build.sh          # after ../base/build.sh: installs the cores and builds identity
----

Each deployable part keeps its deploy values next to its code, in `deploy/apps/<name>`; the Application that deploys it lives in ff-logistic-runtime (xref:ff-logistic::decisions.adoc#d8[decision 8]).
